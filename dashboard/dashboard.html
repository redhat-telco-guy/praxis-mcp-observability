Quick Start See your MCP metrics in OCP Prometheus in 3 steps

Make sure you have sent some requests first! Go to Test Lab and send a few requests, then come back here.

1
Open OCP Console → Observe → Metrics
OCP Console → Observe → Metrics
Make sure the project dropdown at the top says praxis-mcp-test
2
Type praxis_mcp in the query box
Autocomplete will show all 4 MCP metrics:
▶ praxis_mcp_requests_total — all MCP requests
▶ praxis_mcp_tool_calls_total — tool invocations
▶ praxis_mcp_tool_call_duration_seconds — latency
▶ praxis_mcp_filter_rejections_total — rejected
3
Copy a query below, paste it, and click Run Queries
Pick one — control plane or data plane:
CONTROL PLANE Request rate per minute
sum(rate(praxis_mcp_requests_total{method=~"initialize|tools/list|ping|server/discover"}[5m])) * 60
DATA PLANE Tool calls by server
sum by (server) (rate(praxis_mcp_tool_calls_total[5m])) * 60
That’s it! You should see a graph with your MCP metric data.

Troubleshooting: Target not showing UP?

Go to Observe → Targets and search for praxis. You need to see a green UP badge. If it’s missing or shows DOWN, user workload monitoring may not be enabled:

Observe → Targets → Filter: "praxis"
Filter: praxis ● praxis-mcp-test/praxis-ai-metrics/0 Endpoint: http://10.128.2.45:9902/metrics State: UP ← This must be green/UP Labels: app="praxis-ai" namespace="praxis-mcp-test" Scrape: every 15s Last: 3s ago (12ms)
# Check if user workload monitoring pods exist: oc -n openshift-user-workload-monitoring get pods # If empty, enable it: oc apply -f - <<EOF apiVersion: v1 kind: ConfigMap metadata: name: cluster-monitoring-config namespace: openshift-monitoring data: config.yaml: | enableUserWorkload: true EOF # Wait ~60s for pods to start, then check Targets again

Control Plane Queries

See which control plane methods are most frequent

Data Plane Queries
Tool call rate by MCP server (per minute)
Which MCP servers are getting the most tool calls

Tool call rate by tool name
Which specific tools are being invoked most
sum by (tool) (rate(praxis_mcp_tool_calls_total[5m])) * 60
p99 latency by server
Worst-case latency — translator ~500ms, calculator ~20ms
histogram_quantile(0.99, sum by (le, server) (rate(praxis_mcp_tool_call_duration_seconds_bucket[5m])))
p50 (median) latency by server
Typical latency per server
histogram_quantile(0.50, sum by (le, server) (rate(praxis_mcp_tool_call_duration_seconds_bucket[5m])))

Rejection rate
Requests blocked by the MCP filter

Rejection percentage (alert threshold: 10%)
PrometheusRule fires McpHighRejectionRate when this exceeds 10%
sum(rate(praxis_mcp_filter_rejections_total[5m])) / sum(rate(praxis_mcp_requests_total[5m])) * 100

Deployed PrometheusRule Alerts

Go to Observe → Alerting and search for mcp. Three alerts are deployed:

⚠
McpHighRejectionRate
Fires when rejection rate > 10% for 5 minutes
⚠
McpToolCallErrorRate
Fires when tool error rate > 5% for 5 minutes
⚠
McpNoTraffic
Fires when zero MCP requests for 15 minutes

“Inactive” means the conditions aren’t met (good!). Send malformed requests from the Test Lab to trigger McpHighRejectionRate.

Praxis has 71 metrics defined across its full codebase. But metrics are only emitted by filters you actually enable in your config.yaml. On this cluster, we have 3 filters (MCP, Router, Load Balancer), so only ~17 metrics are active. In a production deployment with more filters (rate limiting, auth, circuit breaker, etc.), you’d see more of the 71.

The key point: All 71 metrics cover infrastructure, AI, and routing — but not a single one understands MCP protocol semantics. They can’t tell you which tool was called, which MCP method was used, tool call latency per server, or why an MCP request was rejected.

✗ vs ✓ Which MCP tools are being called and how often?

Existing
No visibility. The proxy sees HTTP POST requests but doesn't parse the JSON-RPC body. You see request_count go up but can't distinguish get_weather from translate.
With MCP Metrics
praxis_mcp_tool_calls_total{tool="get_weather", server="weather-mcp", status="ok"}
Every tool call is individually counted by name, server, and status.

✗ vs ✓ What is the latency per tool / per MCP server?

Existing
filter_duration_seconds measures total filter pipeline time, not individual tool call round-trips. You can't tell if the weather API is fast and the translator is slow.
With MCP Metrics
praxis_mcp_tool_call_duration_seconds{server="translator-mcp", quantile="0.99"} = 0.48
Histogram with p50/p90/p99 per server. Translator p99=480ms, Calculator p99=18ms — immediately visible.

✗ vs ✓ Is this control plane or data plane traffic?

Existing
All MCP requests look identical — HTTP POSTs to the same path. No way to separate initialize/tools/list (control) from tools/call (data).
With MCP Metrics
praxis_mcp_requests_total{method="tools/list"} — tagged by MCP method.
Control plane: initialize, tools/list, ping. Data plane: tools/call.
Operators can set different SLOs for each plane.

✗ vs ✓ Are requests being rejected and why?

Existing
Generic HTTP 4xx/5xx counters. Can't distinguish "invalid JSON-RPC" from "auth failure" from "body too large" from "missing method field".
With MCP Metrics
praxis_mcp_filter_rejections_total{reason="invalid_jsonrpc"}
MCP-specific rejection reasons. PrometheusRule fires alert when rejection rate exceeds 10%.

✗ vs ✓ Which MCP server is handling the most traffic?

Existing
Cluster-level connection metrics exist but don't tell you MCP server identity or which tools are driving load. If weather-mcp is overloaded, you'd see "cluster X has high latency" with no context.
With MCP Metrics
sum by (server) (rate(praxis_mcp_tool_calls_total[5m]))
Instantly shows: weather-mcp: 45 req/min, calculator-mcp: 120 req/min, translator-mcp: 12 req/min.

✗ vs ✓ Can I set up meaningful alerts for MCP traffic?

Existing
You can alert on generic "high error rate" or "high latency" but it covers ALL traffic through the proxy, not just MCP. No way to create "MCP tool call error rate > 5%" or "No MCP traffic for 15 minutes" alerts.
With MCP Metrics
Three production-ready PrometheusRules deployed:
• McpHighRejectionRate — rejection rate > 10% for 5m
• McpToolCallErrorRate — tool call errors > 5% for 5m
• McpNoTraffic — zero MCP requests for 15m

Full MCP Observability

Praxis ships 71 metrics covering infrastructure, AI, and routing — a strong foundation. But not one of them understands MCP protocol semantics. These 4 new metrics + 3 PrometheusRule alerts + 21-panel Grafana dashboard close the only remaining observability gap — giving operators the same protocol-level visibility into MCP traffic that Envoy gives for HTTP/gRPC.
